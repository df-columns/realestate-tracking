# 서울·수도권 급지별 실거래가 추이

99개 단지의 전용 59㎡ / 84㎡ 실거래가(매매·전세·전세가율)를 표와 차트로 비교하는 도구.
로컬에서 그냥 열어도 되고, Firebase Hosting 에 올려 URL 하나로 공유해도 된다.

- **삼토시50** — 첨부한 권역별 단지 목록 50개
- **급지 대표 48개 단지** — 수도권 급지표(1~10급지)를 설명하는 대표 단지 (서울 + 경기 12곳)

```
index.html          # 결과 화면 (데이터를 fetch 로 읽는다)
collect.py          # 국토부 실거래가 API 수집 → 집계
enrich.py           # 단지 제원(세대수·준공연월) 수집
complexes.py        # 조회 대상 99개 단지 + 급지 + 매칭 규칙
make_sample.py      # 화면 확인용 샘플 데이터 생성기
publish.py          # Firebase Hosting 배포 (public/ 빌드 + deploy)
firebase.json       # Hosting 설정 (CORS·캐시 헤더)
data/apt_data.json  # 화면이 읽는 데이터 — Firebase 에 올라가는 원본
data/apt_data.js    # 같은 데이터의 오프라인 폴백 (file:// 로 열 때)
data/match_report.md  # 단지명 매칭 결과 리포트
public/             # 배포 산출물 (publish.py 가 매번 새로 만듦, git 제외)
cache/              # 구·월 단위 원본 캐시 (재실행 시 재사용)
apikey.txt          # 공공데이터포털 서비스 키 (git 제외)
```

## 사용법

```bash
py -3 collect.py                 # 최근 10년 매매+전월세 수집 → data/apt_data.json
py -3 collect.py --start 202101  # 기간 지정
py -3 collect.py --types trade   # 매매만
py -3 collect.py --aggregate-only  # 재수집 없이 캐시로 재집계
```

수집 후 `index.html` 을 브라우저에서 연다. 캐시가 남아 있으므로 다음 달 갱신 시에는
새 달치만 받아온다.

## Firebase Hosting 배포

데이터를 Firebase 에 올려두면 `index.html` 파일 하나만 있어도(심지어 더블클릭으로
`file://` 로 열어도) 화면이 뜬다. 데이터를 같이 들고 다닐 필요가 없다.

### 준비 (한 번만)

```bash
npm i -g firebase-tools     # 이미 있으면 생략
firebase login
firebase use --add          # 프로젝트 선택 → .firebaserc 생성
```

### 배포

```bash
py -3 collect.py            # 데이터 갱신
py -3 publish.py            # public/ 빌드 + firebase deploy
```

`publish.py` 가 하는 일:

1. `public/` 을 비우고 `index.html` + `data/apt_data.json` **둘만** 넣는다.
   `apikey.txt`, `cache/`, `*.py` 는 구조적으로 올라갈 수 없다.
2. `public/index.html` 의 `REMOTE_DATA_URL` 을 실제 Hosting 주소로 채운다.
3. `firebase deploy --only hosting` 실행.

끝나면 두 가지가 생긴다.

- **공유 URL** — `https://<프로젝트ID>.web.app/`
- **공유용 단일 파일** — `public/index.html`
  이 파일만 메신저로 보내면 받는 사람은 그냥 열어서 본다 (데이터는 Firebase 에서 받음).

옵션: `--build-only` (배포 없이 빌드만), `--project <ID>`, `--site <사이트명>`.

### CLI 로그인이 안 될 때 — Cloud Shell 로 배포 (권장 우회로)

Firebase 콘솔 안에 브라우저 터미널(Cloud Shell)이 있고, 거기의 firebase CLI 는
**콘솔에 로그인한 계정으로 이미 인증돼 있다.** `firebase login` 을 할 필요가 없다.

```bash
py -3 publish.py --zip --project <프로젝트ID>
```

`dist/deploy-<프로젝트ID>.zip` (약 220KB) 이 나온다. 안에 `firebase.json` 과
`public/` 만 들어 있다. 그다음 브라우저에서:

1. `https://console.firebase.google.com/project/<프로젝트ID>/hosting`
2. 우측 상단 Cloud Shell 아이콘 `>_` 클릭 — 아래에 터미널이 열린다
3. 터미널 우측 위 `⋮` → **업로드** → 파일 → 위 zip 선택
4. 터미널에 세 줄 붙여넣기

```bash
unzip -o deploy-<프로젝트ID>.zip -d apt
cd apt
firebase deploy --only hosting --project <프로젝트ID>
```

Cloud Shell 홈 디렉터리는 세션이 끊겨도 남으므로, 다음 달 갱신 때는 새 zip 만 올리고
같은 세 줄을 다시 실행하면 된다. CLI 버전이 낮다는 경고가 나오면 마지막 줄을
`npx firebase-tools@latest deploy --only hosting --project <ID>` 로 바꾼다.

### 데이터만 콘솔에 올리는 방법 (Hosting 자체를 안 쓸 때)

`firebase login` 이 사내망/정책 때문에 막히면, Hosting 을 건너뛰고 **데이터만** 웹
콘솔에서 올린 뒤 그 주소를 index.html 에 박아 넣으면 된다. Hosting 콘솔에는 파일
업로드 기능이 없지만, Storage 와 Realtime Database 는 브라우저에서 바로 올라간다.

```bash
py -3 publish.py --data-url "https://.../apt_data.json"
```

`dist/index.html` 하나가 나온다. 더블클릭하면 그 URL 에서 데이터를 받아 화면이 뜬다.
배포는 하지 않고, 실행 전에 URL 이 실제로 읽히는지 한 번 확인해 준다 (`--no-check` 로 생략).

| 저장소 | 올리는 법 | 데이터 URL | 주의 |
|---|---|---|---|
| Cloud Storage | 콘솔 → Storage → 파일 업로드 | 파일 클릭 → 다운로드 URL 복사 | 2024-10 이후 만든 프로젝트는 Blaze(카드 등록) 필요할 수 있음. CORS 는 기본 허용(`ACAO: *`) |
| Realtime Database | 콘솔 → Realtime Database → ⋮ → JSON 가져오기 | `https://<DB>.firebaseio.com/.json` | Spark(무료) 가능. `null` 필드는 저장 시 사라지지만 화면 코드가 전부 `!= null` 검사라 무해 (배열 안 `null` 은 0건) |

어느 쪽이든 읽기 규칙을 공개로 열어야 한다 (Storage `allow read: if true;`,
RTDB `".read": true`). 국토부 공개 실거래가라 문제는 없지만 쓰기는 닫아 둘 것.


### 데이터 로딩 순서

`index.html` 은 아래 순서로 첫 성공까지 시도한다.

기준은 `location.protocol` 이다.

| 상황 | 1순위 | 2순위 | 3순위 |
|---|---|---|---|
| 웹 (Hosting · Pages · 로컬 서버) | `data/apt_data.json` (같은 폴더) | `data/apt_data.js` | Firebase (`REMOTE_DATA_URL`) |
| `file://` (떼어 온 단일 파일) | Firebase (`REMOTE_DATA_URL`) | `data/apt_data.json` | `data/apt_data.js` |

웹으로 열렸으면 자기 폴더가 우선이다. 자기 데이터가 없거나 일시적으로 안 받아질 때
(Pages 재빌드 중 503 을 실제로 겪었다) Firebase 가 받아 준다.
`file://` 은 옆에 데이터가 없는 게 정상이라 Firebase 를 먼저 봐서 헛된 404 를 안 낸다.

`file://` 에서는 상대경로 `fetch` 가 브라우저에 막힌다. 그래서 배포 전 로컬에서 보려면
`data/apt_data.js` 폴백(스크립트 태그)이 받아준다. `collect.py` 는 `.json` 과 `.js` 를
함께 쓴다.

크로스 오리진 `fetch` 는 `firebase.json` 의 `Access-Control-Allow-Origin: *`
헤더(`/data/**`)로 열어 뒀다. 데이터는 5분 캐시, `index.html` 은 `no-cache`.

> 공개 범위: Hosting 은 URL 을 아는 사람 누구나 접근한다. 국토부 공개 실거래가라
> 문제는 없지만, 비공개가 필요하면 Firebase Auth + Firestore 로 옮겨야 한다.

## 보는 방법 세 가지

같은 화면을 세 경로로 볼 수 있다. 데이터는 한 파이프라인에서 나온다.

| 경로 | 주소 | 데이터 출처 |
|---|---|---|
| Firebase Hosting | `https://realestatetracking-89d37.web.app/` | 같은 사이트의 `data/apt_data.json` |
| GitHub Pages | `https://df-columns.github.io/realestate-tracking/` | 리포에 커밋된 `data/apt_data.json` |
| 파일 하나 | 위 주소에서 저장한 `index.html` | Firebase (파일에 주소가 박혀 있다) |

세 번째가 이 프로젝트의 원래 목표다. 배포된 사이트에서 받은 `index.html` 은
**데이터 폴더 없이 파일 하나만으로**, `file://` 로 그냥 열어도 동작한다.
실제 Chrome 에서 검증했다 (단지 99개·급지 지도·체크박스 198개 렌더 확인).

```bash
curl -o index.html https://realestatetracking-89d37.web.app/
```

껍데기만 파일이고 데이터는 매번 Firebase 에서 받으므로, 파일을 다시 보내지 않아도
받는 사람은 늘 최신 데이터를 본다. 화면 기능을 고쳤을 때만 파일을 다시 주면 된다.

소스 `index.html` 의 `REMOTE_DATA_URL` 에도 Firebase 주소가 들어 있으므로 리포에서 받은
파일도 그대로 동작한다. `publish.py` 는 배포할 때 그 줄의 값을 그때의 주소로 다시 쓴다.

## 자동 갱신

역할이 둘로 나뉜다. **수집은 이 PC, 배포는 GitHub Actions.**

```
 이 PC (작업 스케줄러)                    GitHub                      결과
 daily.bat
   └ update.py --recent 3 --push
       수집 → 재집계 → 검증 ──┐
                              └ git push ─┬─ Pages 자동 재빌드 ──→ github.io
                                          └─ deploy.yml ────────→ web.app
```

### 왜 수집을 클라우드에서 못 하나

국토부 API(`apis.data.go.kr`)가 **GitHub 러너에서 접속이 안 된다.** 2026-08-20 실측:

```
!! 실패 trade 11110 201707 p1: HTTPSConnectionPool(host='apis.data.go.kr', port=443):
   Max retries exceeded ...
```

80건 전부 같은 오류, 성공 0건, 60분 타임아웃으로 취소. 해외 클라우드 IP 차단으로 보인다.
같은 코드를 이 PC 에서 돌리면 **66요청 실패 0건 · 8.0 req/s · 감속 0회** 로 끝난다.
그래서 수집은 국내에서만 한다.

### 왜 매일 돌려도 부담이 없나

| 작업 | API 요청 수 |
|---|---|
| 전체 수집 (10년 × 33개 시군구 × 2종) | 약 7,200회 |
| 최근 3개월만 재수집 | 약 300회 |
| 캐시로 10년치 재집계 | 0회 |

신고 기한(계약 후 30일) 때문에 **변하는 건 최근 몇 달뿐이다.** 일일 한도(보통 10,000회)
대비 3% 수준이다.

### 상시 켜두는 PC 에 설치하기 — 폴더 복사 방식 (권장)

이 PC 에서 꾸러미를 만들고, 그 폴더를 상시 PC 로 복사한 뒤 '설치.bat' 을 더블클릭한다.
git 도, SSH 배포키도, 리포 clone 도 필요 없다.

```bash
py -3 bundle.py                # dist/수집기.zip  (51MB, 파일 하나)
py -3 bundle.py --no-cache     # dist/수집기.zip  (0.3MB — 첫 실행이 10년 전체를 받는다)
py -3 bundle.py --no-zip       # 폴더만
```

옮기는 건 **zip 하나**다. 폴더 안 파일이 7,272개로 보이지만 7,260개는 `cache/` 안의
압축 데이터이고, 사람이 볼 파일은 11개다.

캐시를 함께 담는 쪽을 권한다. 51MB 를 한 번 옮기면 상시 PC 에서 10년 전체 수집
(약 7,200요청 · 15~20분)을 하지 않는다. `--no-cache` 로 0.3MB 만 옮겨도 되고, 그때는
`설치.bat` 이 캐시가 없는 것을 보고 첫 실행을 전체 수집으로 돌린다.

폴더에 든 것

| 파일 | 용도 |
|---|---|
| `설치.bat` | 사람이 한 번 누른다. 파이썬·토큰 확인 → 라이브러리 → 시험 실행 → 자동 실행 등록 |
| `지금갱신.bat` | 즉시 갱신하고 로그 끝부분을 보여준다 |
| `자동실행끄기.bat` | 스케줄 해제 |
| `update.bat` | 스케줄러가 부르는 실제 작업 (ASCII 이름 — bat 안에서 한글 파일명 참조를 피한다) |
| `시작할때갱신.bat` | 시작 폴더(`shell:startup`)에 바로가기를 넣어 두면 PC 를 켤 때마다 한 번 돈다 |
| `token.txt` | GitHub 토큰. 처음 한 번 붙여넣는다 |
| `읽어보세요.txt` | 3줄 안내 |
| `cache/` | 67MB. 이게 있어서 상시 PC 에서 10년 전체 수집을 다시 하지 않는다 |

그 PC 에 필요한 것은 **파이썬 하나**다. `git push` 대신 GitHub Contents API 로
`data/apt_data.json` 한 파일만 PUT 하기 때문이다(`push_github.py`). `update.py` 는
`.git` 과 `git` 이 둘 다 있으면 git 으로, 없으면 API 로 올린다.

토큰은 fine-grained PAT 하나면 된다 — Repository access 를 `realestate-tracking`
하나로, Permissions 의 Contents 를 Read and write 로. 그 리포의 파일만 고칠 수 있다.
`설치.bat` 이 필요할 때 발급 페이지와 메모장을 열어 준다.

**꾸러미에 `apikey.txt` 가 들어 있으니 폴더를 외부에 공유하지 말 것.**

윈도우 인코딩 때문에 두 가지를 맞춰 뒀다. bat 은 cp949(BOM 없음, CRLF) — UTF-8 BOM 이
붙으면 cmd 가 첫 줄을 명령으로 읽어 에러를 낸다. 파이썬 출력도 `PYTHONIOENCODING=cp949:replace`
로 콘솔과 맞췄다 — 안 맞추면 한 창에서 한쪽 한글이 깨진다.

### 리포를 clone 해서 설치하기 (개발용)

수집은 한국 네트워크에서만 나갈 수 있다. 상시 켜둔 PC 가 있으면 그게 가장 낫다 —
주말·휴가에도 돌고, 클라우드 가입이나 카드가 필요 없다.

그 PC 에서 **한 번만** 실행한다.

```powershell
# 이 리포를 아무 데나 받아서 스크립트만 꺼내 쓰거나, 아래 한 줄로 바로
irm https://raw.githubusercontent.com/df-columns/realestate-tracking/main/setup_runner.ps1 -OutFile setup_runner.ps1
powershell -ExecutionPolicy Bypass -File setup_runner.ps1
```

스크립트가 순서대로 한다.

| 단계 | 하는 일 |
|---|---|
| 1 | python · git · ssh-keygen 확인 (없으면 설치 링크를 알려주고 멈춘다) |
| 2 | 배포키 생성 → 공개키를 찍어 주고 리포에 등록하라고 멈춘다 |
| 3 | clone 후 **푸시 권한을 그 자리에서 확인** (`push --dry-run`) |
| 4 | `requests` · `truststore` 설치 |
| 5 | `apikey.txt` 확인 — 없으면 붙여넣게 한다 |
| 6 | 국토부 API 실제 호출 1건으로 접속 확인 |
| 7 | 첫 수집 — 캐시가 없으면 10년 전체(약 7,200요청 · 15~20분) |
| 8 | 작업 스케줄러에 매일 04:37 등록 |

왜 배포키인가: 무인 실행에서는 Windows 자격 증명 관리자를 못 읽을 수 있다. 배포키는
파일이라 로그오프 상태에서도 동작하고, **이 리포 하나에만** 쓰기 권한이 있어 계정
전체가 걸리지 않는다. 등록은 `Settings → Deploy keys` 에서 하고 *Allow write access*
를 반드시 켠다.

캐시 67MB 를 이 PC 에서 복사해 가면 7단계의 전체 수집을 건너뛸 수 있다. 안 옮겨도
한 번의 전체 수집은 일일 한도(보통 10,000회) 안에 들어간다.

설치 후:

```
schtasks /run /tn "실거래가 갱신"      # 즉시 실행
schtasks /delete /tn "실거래가 갱신" /f  # 해제
type daily.log                          # 로그
```

### 이 PC 에 직접 등록할 때

```
schtasks /create /tn "실거래가 갱신" /sc daily /st 06:30 /f /tr "\"C:\Users\sw.shin\Desktop\claude code 프로젝트\027_실거래가 추이\daily.bat\""
```

경로에 공백이 있어 `/tr` 값 안쪽을 `\"` 로 한 번 더 감싼다. cmd.exe 에서 실행한다.

놓친 실행을 따라잡게 하려면 작업 스케줄러 UI 에서 해당 작업 → 설정 →
**예약 시작 시간을 놓친 경우 가능한 즉시 작업 시작** 을 켠다.
실행 기록은 `daily.log` 에 쌓인다.

### 불규칙하게 켜고 끄는 PC 에서도 매일 돌게

`설치.bat` 이 자동으로 처리한다. 세 가지를 맞춘다.

| 설정 | 없으면 |
|---|---|
| `/ru SYSTEM` 으로 등록 | 그 사용자가 로그온해 있을 때만 돈다 |
| `StartWhenAvailable=True` | 04:37 에 꺼져 있었으면 **그날은 건너뛴다** (기본값이 False) |
| `WakeToRun=True` | 절전이면 안 돈다 |

결과: **PC 가 하루에 한 번이라도 켜지면 그날 몫이 실행된다.** 누가 켜든, 로그온을
하든 안 하든 무관하다. 등록된 작업을 확인하면 이렇게 나온다.

```
UserId=SYSTEM  StartWhenAvailable=True  WakeToRun=True  ExecutionTimeLimit=PT2H
```

SYSTEM 계정에는 `py` 런처가 PATH 에 없다. 그래서 `설치.bat` 이 python.exe 절대경로를
`pyexe.txt` 에 적어 두고 `update.bat` 이 그걸 읽는다. 파이썬이 사용자 폴더에 설치돼
있어도 SYSTEM 이 읽을 수 있어 문제없다 — 실제로 SYSTEM 컨텍스트에서
`requests`·`truststore` import 까지 확인했다.

관리자 권한 없이 실행하면 SYSTEM 등록이 실패하고 현재 사용자로 등록된다. 그때는
그 사용자가 로그온해 있어야 돈다.

**시작 폴더에 넣는 방법 (선택)**

`시작할때갱신.bat` 의 **바로가기**를 `Win+R` → `shell:startup` 에 넣는다.
`지금갱신.bat` 을 넣으면 안 된다 — 끝에 `pause` 가 있어 부팅마다 창이 남는다.
`시작할때갱신.bat` 은 창을 최소화해 띄우고, 부팅 직후 네트워크가 안 붙은 상태를
피하려 3분 기다린 뒤 돈다.

2번은 1번을 대신하지 못한다. PC 를 며칠 안 껐다 켜면 로그온이 없어 시작 폴더는
안 돌고, 그때는 매일 작업이 받아 준다. 완전히 꺼진 PC 는 무엇으로도 깨울 수 없다.

### 공백이 생겼을 때 (휴가·PC 꺼짐)

PC 가 며칠~몇 달 꺼져 있어도 **돌아온 첫 실행이 스스로 메운다.** `update.py` 는 기존
데이터에서 거래가 잡힌 마지막 달을 읽어, 그 달부터 이번 달까지를 덮을 만큼 요청 창을
넓힌다. 상한은 12개월이고 그보다 크면 `--full` 을 권하는 문구를 띄운다.

| 공백 | 요청 창 |
|---|---|
| 1개월 (한 달 휴가) | 3개월 (기본값이 이미 덮는다) |
| 3개월 | 4개월 |
| 6개월 | 7개월 |
| 13개월 이상 | 12개월 + `--full` 권고 |

공백 동안 두 사이트는 계속 열리고 마지막 스냅샷을 보여준다. '신규 거래' 탭은 최신
거래가 한 달 넘게 없으면 안내문에 갱신이 밀렸다고 적는다.

`update.py` 는 배포 전에 결과를 검증한다. 단지 90개 미만, 기간 9년 미만, 거래
15,000행 미만, 가장 이른 거래가 시작월보다 12개월 이상 늦음, 최근 3개월 거래 0건 —
하나라도 걸리면 **푸시하지 않고** `data/apt_data.json` 을 갱신 전으로 되돌린다.
최근 몇 달만 받는 중간 단계에서 데이터가 잠깐 짧아지는데, 그 상태가 배포되는 걸
막기 위한 장치다.

### 데이터 갱신 주기

국토부 실거래가는 계약일 기준으로 등록되며, 신고 기한(계약 후 30일) 때문에
**직전 1~2개월 데이터는 계속 늘어난다.** 최근 두 달은 `--refresh` 로 다시 받는 편이 좋다.

## 화면

헤더에 데이터가 언제 것인지 적힌다.

```
2017.08 ~ 2026.08 · 단지 99개 · 최신 거래 2026.08.19 · 오늘 갱신 (2026-08-20)
```

**최신 거래**와 **갱신 시점**은 다르다. 신고 기한(계약 후 30일) 때문에 오늘 받아도
마지막 거래는 며칠 전일 수 있다. 갱신이 3일 이상 밀리면 헤더에 주황색 경고가 붙는다
(`데이터가 12일 전입니다 — 수집이 멈춘 듯합니다`). 자동 수집이 멈춘 걸 모르고 옛
데이터를 보는 상황을 막기 위한 것이다.

**전역 필터 — 관찰기간 / 전용면적(59·84) / 집계 단위 / 보정.**
아래 모든 탭이 같은 조건으로 다시 그려진다.

관찰기간은 세 방식으로 정한다.

| 방식 | 값 |
|---|---|
| 연도별 | `YTD`(전년 12월 → 최신월) · 최근 5개 완결 연도 (`2025년`~`2021년`) |
| 기간지정 | `6개월` `1년` `2년` `3년` `5년` `10년` `전체` (최신월에서 거꾸로) |
| 직접 | 연/월 드롭다운 네 개 (칩 선택은 해제된다) |

연도칩은 데이터 범위에서 자동으로 만들어지므로 해가 바뀌면 목록도 따라 바뀐다.

`직접` 은 `input[type=month]` 가 아니라 연/월 드롭다운을 쓴다. 브라우저 기본 월 입력은
연 칸과 월 칸을 따로 눌러야 해서 번거롭다. 드롭다운은 해당 연도에 **데이터가 있는 달만**
보여주므로 범위를 벗어난 값을 고를 수 없고, 시작이 종료보다 늦어지면 자동으로 뒤바꾼다.

### 거래 공백으로 선이 끊길 때

단지별 월 거래가 0~3건이라 그냥 그리면 선이 조각난다. 세 가지로 대응한다.

| 컨트롤 | 하는 일 |
|---|---|
| **집계** `월 / 분기 / 연` | 월별 값을 분기·연으로 묶는다. 거래가 드문 단지도 대체로 이어진다 |
| **보정** `원값 / 3 / 6 / 12개월` | 이동중앙값 창. `원값`은 그 달 값 그대로, 나머지는 앞뒤 달과 함께 중앙값을 내 다듬는다. 창이 넓을수록 부드럽고 빈 달도 메워지지만 고점·저점이 눌린다 |
| 공백 연결선 (자동) | 그래도 남는 공백은 **얇고 흐린 선**으로 잇는다. 실제 관측 구간은 2px 굵은 선이라 어디가 실측이고 어디가 추정인지 구분된다 |

거래가 아주 드문 단지(압구정 신현대 84㎡ 등)는 `분기` + `6개월 보정`이 잘 맞는다.
빈 달을 직전 값으로 채우는 방식(carry-forward)은 없던 거래를 있는 것처럼 보이게 하므로
쓰지 않았다.
급지 지도의 변동률·칸 색은 **이 관찰기간의 시작 → 끝 변동**이다. `2024년`을 고르면
2024.01 → 2024.12 한 해 변동으로, `YTD`를 고르면 전년말 대비 변동으로 전체가 다시 계산된다.

### 1. 급지 지도 (기본 화면)

첨부한 수도권 급지표를 그대로 옮긴 화면. **행 = 급지(1~10), 칸 = 단지**다.

- 급지 머리: 그 급지 단지들의 **중위 가격**, 변동률, 단지 수, 급지표의 지역명, 사이클 스파크라인
- 각 칸: 단지명 + 관찰기간 끝 시점 가격 + 그 기간 변동률. **칸 색이 변동률**(초록 상승 / 빨강 하락, 3단계)
- `칸에 표시`: 매매가 / 전세가 / 평당가 / 전세가율
- **칸을 누르면 상세 팝업** — 그 단지의 매매가·전세가·전세가율 추이 3개 차트와
  최근값·기간 변동·전고점 대비·거래건수가 한 번에 뜬다. `Esc`나 바깥을 누르면 닫힌다.
- **칸 좌상단 체크박스** — 비교할 단지를 담는다. 담으면 상단에 `선택 N개 비교하기 →`
  버튼이 생기고, 누르면 단지 비교 탭으로 넘어간다.
- 칸에 마우스를 올리면 그 단지의 매매·전세·전세가율·연식·거래건수가 요약으로 뜬다
- 상세 팝업의 차트는 **관찰기간과 무관하게 항상 최근 5년**이다(단지 자체 흐름을 보는 화면이라서)
- 거래가 부족한 단지(기준월 전 12개월 내 거래 없음)는 회색으로 `거래 부족` 표시

숫자를 다 읽지 않고도 급지 간 서열과 최근 1년 흐름이 한 장에 들어온다.
예를 들어 1급지만 마이너스(-1.7%)이고 5~9급지가 +20%대로 물든 그림이면
"상급지 조정 · 중하급지 추격" 국면이라는 게 색만 봐도 읽힌다.

### 2. 신규 거래

최근 1~3개월 사이에 **체결된 개별 거래**를 급지별로 묶어 보여준다. 급지 지도가
"지금 이 단지는 얼마인가"를 보는 화면이라면, 이쪽은 "방금 무슨 거래가 붙었나"를 본다.

한 칸이 한 건이다. 단지명 · 체결가 · 거래일 · 층 · 변동률이 들어간다.
변동률은 **그 거래 직전 12개월 월중위값 대비**이고, 칸 색도 그 값으로 칠한다.
직전 시세보다 비싸게 붙었으면 초록, 싸게 붙었으면 빨강이다.

| 컨트롤 | 값 |
|---|---|
| 기간 | 1개월 · 2개월 · 3개월 (기본 2개월) |
| 거래유형 | 매매 · 전세 |
| 정렬 | 최신순 · 가격순 · 변동률순 |

기간은 **위쪽 관찰기간 설정과 무관하게 항상 오늘에서 거꾸로 자른다.** 달 단위가 아니라
날짜 단위라(예: 2026.06.20 ~ 2026.08.20) 이번 달 거래가 바로 들어온다. 관찰기간을
6개월이나 10년으로 바꿔도 이 탭은 그대로다.

그래서 `collect.py` 는 **이번 달까지** 받는다. 신고 기한(계약 후 30일) 때문에 이번 달은
아직 덜 찬 상태다 — 다 찬 달이 월 1,000건 남짓인데 8월 20일 기준 8월분은 319건이었다.
덜 찼다는 건 급지 머리의 건수로 드러난다.

전용면적은 상단 전역 필터(59·84)를 따른다. 급지가 없는 단지는 급지별로 묶을 수
없으므로 제외한다. 칸을 누르면 그 단지의 상세 팝업이 열린다.
최신 거래가 한 달 넘게 없으면 안내문이 갱신이 밀렸다고 알린다.

데이터는 `collect.py` 가 `apt_data.json` 에 `recent` 항목으로 싣는다. 최근
`RECENT_MONTHS`(기본 4)개월치 개별 거래다. 화면이 날짜로 자르는 창이 달 경계를
걸치므로 달 단위로는 한 달 더 담아 둔다. 약 3,800건 · gzip 15KB 정도다.
이 항목이 없는 옛 데이터로 열면 탭이 안내 문구를 띄운다.

### 3. 그룹 추이

맨 위에 **기간 변동 히트맵**이 있다. 행이 급지(1~10), 열이 연도(집계를 `분기`로 두면 분기),
칸이 그 기간의 중위가 변동률이다. 색으로 급지를 구분하지 않으므로 10개 급지를 한 화면에
놓고 **언제 어떤 급지가 뛰고 눌렸는지**를 볼 수 있다. 열마다 1위 칸에 테두리가 있고,
맨 오른쪽 `전 구간` 열은 누적 변동이다. 이 히트맵만은 관찰기간과 무관하게 전 구간을 본다.

그 아래는 **급지별** 또는 **권역별**로 묶은 중위가 추이 차트다.

마지막으로 **기준 급지 대비 갭·비율 추이** 두 차트가 있다. `갭 기준` 드롭다운으로 기준 급지를
고른다(기본 6급지, 권역 모드면 기준 권역).

- **갭 추이** — 각 급지 중위가 − 기준 급지 중위가. 0 선이 기준 급지다. 절대 금액 격차가
  얼마나 벌어졌는지 본다.
- **비율 추이** — 기준 급지를 100%로 놓은 배율. 갭이 벌어져도 비율이 그대로면 같은 배수로
  함께 오른 것이고, 비율이 올라가면 기준 급지보다 더 빨리 오른 것이다.

두 차트를 같이 봐야 한다. 상급지는 금액이 크니 같은 비율로 올라도 갭은 훨씬 크게 벌어진다.
`비율`이 진짜 상대 강도를 말해준다. 급지는 한 번에 8개까지 선택
(기본 1·3·5·7·10급지). 가격대가 다른 급지를 나란히 볼 때는 지표를 **지수(=100)** 로
바꾸는 편이 읽기 쉽다. 아래에 그룹별 단지 스파크라인이 붙는다.

**급지별 기간 변동 히트맵** — 행이 급지(또는 권역), 열이 연도(집계가 분기면 분기)다.
각 칸은 그 기간의 중위가 변동이고, 열마다 가장 많이 오른 칸에 테두리를 둘렀다.
연도별 칸은 관찰기간과 무관하게 전 구간을 보여준다.

오른쪽에 요약 두 열이 붙는다.

| 열 | 구간 |
|---|---|
| **선택기간** | 위쪽 관찰기간으로 자른 구간. 칩을 바꾸면 따라 바뀐다 |
| **전 구간** | 데이터 전체 |

관찰기간이 전 구간과 같아도(`전체` 선택) 선택기간 열은 그대로 둔다. 값이 겹치는
중복보다, 찾는 열이 사라져 보이는 편이 나쁘다. 두 열에도 1위 테두리가 붙어 어느
급지가 앞섰는지 바로 보인다.

### 4. 단지 비교

최대 8개 단지를 겹쳐 비교한다. 두 가지 모드가 있다.

- **3종 함께** — 매매가·전세가·전세가율을 세 개 차트로 나란히. 같은 단지는 같은 색이다.
  축 단위가 다른 값을 한 그림에 겹치면 없는 상관관계가 생기므로 세 개로 나눴다.
- **선택 지표만** — 지표 하나를 크게.

**기준 단지**를 고르면 매매·전세 차트가 그 단지를 100%로 놓은 **상대가격**으로 바뀐다.
예: 반포자이를 기준으로 두면 헬리오시티 62%, 남산타운 38%, 북한산아이파크 22% 처럼
급지 간 격차와 그 격차가 시간에 따라 벌어졌는지 좁혀졌는지가 한눈에 보인다.
기준 단지에 그 달 거래가 없으면 12개월 안의 가까운 거래로 메운다.
요약표에도 `<기준단지> 대비` 열이 붙는다.

지표 중 **지수(=100)** 는 선택 기간 첫 거래를 100으로 놓아 가격대가 다른 단지의
상승률을 같은 축에서 비교한다. **전세가율**은 전세 중위값 ÷ 매매 중위값이다.

차트 아래 **CSV 내려받기** 로 차트에 쓰인 월별 값을 그대로 받을 수 있다.

### 5. 상세 표

**한 행 = 한 단지**. 매매가 · 전세가 · 전세가율을 세 개의 열 묶음으로 나란히 보여준다.
각 묶음은 `현재값`과 선택한 구간의 변동률로 구성된다.

- **변동 구간을 직접 세팅** — 1개월·3개월·6개월·1년·2년·3년·5년·10년 칩을 켜고 끄거나,
  `직접` 칸에 `1,3,6,12,36` 처럼 개월 수를 넣는다. 기본은 1년·3년·5년.
- **기준 시점은 전역 필터의 종료월(모든 단지 공통)**. 종료월을 2022-10 으로 바꾸면
  그 시점 기준으로 표 전체가 다시 계산된다. 기준월에 거래가 없는 단지는 12개월 안의
  최근 거래를 쓰고 현재값 아래에 그 달을 적는다(12개월 안에도 없으면 행에서 빠진다).
  단지별 마지막 거래월을 기준으로 하면 표에서 서로 비교가 안 되므로 이렇게 맞췄다.
- 변동 칸은 **변동률 + 그 시점의 실제 값**을 함께 보여준다.
- **연식** — 준공연월과 "지은지 N년 M개월". 준공 월 정보가 없으면 실거래 자료의
  건축년도로 연 단위 근사값을 쓴다(`약 N년`).
- **세대수** — `enrich.py` 를 실행해야 채워진다(아래 참고).
- 전세가율 열의 변동은 **%p**(퍼센트포인트) 차이다.
- 급지 칩·단지 구분(`삼토시50+급지대표` / `삼토시50`)·검색으로 행을 좁힌다.
- **급지 구간 배경** — 홀수 급지에만 파란 띠를 깔아 인접 구간이 갈리게 했고,
  띠의 진하기는 급지 순서를 따른다(1급지가 가장 진함). 급지로 정렬했을 때는
  구간마다 머리행이 붙는다.
- 열 제목을 누르면 그 열로 정렬된다(급지·연식·세대수·각 지표 변동률 모두).
- 단지명을 누르면 그 단지가 비교 차트에 추가된다.
### 단지 상세 팝업

지도나 표에서 단지를 누르면 열린다. 차트만으로는 실제 체결이 안 보이므로 표를 함께 둔다.

- **차트** — 매매가 · 전세가 · 전세가율, 최근 5년 (관찰기간과 무관하게 고정)
- **체결 내역** — 개별 거래. 거래일 · 유형 · 체결가 · 층 · 직전 12개월 대비
- **월별 실거래** — 보정 없는 원값. 월별 중위 · 건수 · 최저~최고 · 전세가율

### 급지 분류를 고치려면

`complexes.py` 각 단지의 급지 숫자만 바꾸면 된다(데이터 재수집 불필요,
`py -3 collect.py --aggregate-only` 로 재집계). 급지표의 경계 지역은 판단이
갈리므로 원하는 기준으로 조정해서 쓰면 된다.

## 지역코드 주의

**화성시는 2025년 구 신설로 41590 이 비었다.** 41591(남양·향남) / 41593(봉담) /
41595(병점·반월) / **41597(동탄)** 로 나뉘어 있어 동탄 단지는 41597 로 받는다.
다른 지역을 추가할 때 `items=0` 이 나오면 같은 이유일 수 있으니 하위 코드를 확인한다.

## 집계 규칙 (알아둘 것)

- **대표 면적 자동 선택** — 59㎡는 52~68㎡, 84㎡는 74~92㎡ 구간의 거래 중
  가장 많이 거래된 면적군 하나를 골라 그 타입만 쓴다(±1.0㎡). 은마(76.8㎡)처럼
  정확히 59/84가 아닌 노후 단지도 국평 계열이 잡히도록 한 것. 실제 선택된 면적은
  화면과 `data/match_report.md` 에 표시된다.
- **월별 중위값** — 평균은 층·향 편차에 흔들려서 중위값을 쓴다. 단지별 월 거래가
  0~3건이라 기본으로 3개월 이동중앙값을 적용한다(끌 수 있음).
- **제외** — 매매는 해제된 거래(`cdealType='O'`), 전월세는 월세가 있는 계약은 뺀다(순수 전세만).
- **단지명 매칭** — 실거래 데이터의 아파트명은 표기가 제각각이라(`래미안 원베일리`,
  `성산시영(유원)`, `한신,한진`) `complexes.py` 의 별칭·법정동으로 맞춘다.
  수집 후 `data/match_report.md` 에서 매칭 0건인 단지를 확인해 별칭을 보정하고
  `--aggregate-only` 로 다시 집계하면 된다.

## 세대수·준공연월 (enrich.py)

실거래 자료에는 건축년도(연)만 있고 세대수가 없다. 아래 두 API를 추가로
활용신청하면 정확한 준공연월과 총 세대수를 붙일 수 있다.

- 국토교통부_공동주택 **단지 목록**제공 서비스 (`AptListService3`)
- 국토교통부_공동주택 **기본 정보**제공 서비스 (`AptBasisInfoServiceV4`)

```bash
py -3 enrich.py                    # data/complex_info.json 생성
py -3 collect.py --aggregate-only  # 화면에 반영
```

키가 아직 등록되지 않았으면 스크립트가 어떤 API를 신청해야 하는지 알려주고 멈춘다.

## 서비스 키

`apikey.txt` 에 공공데이터포털 **일반 인증키(Decoding)** 를 한 줄로 넣는다.
필요한 API 두 가지를 각각 활용신청해야 한다.

- 국토교통부_아파트 매매 실거래가 상세 자료 (`RTMSDataSvcAptTradeDev`)
- 국토교통부_아파트 전월세 실거래가 자료 (`RTMSDataSvcAptRent`)

`SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 가 나오면 아직 키가 활성화되지 않았거나
해당 API에 활용신청이 안 된 상태다(신청 직후 1~2시간 소요).

## 사내망 SSL

사내 SSL 검사 프록시 때문에 인증서 검증이 실패하므로 `truststore` 로 윈도우
인증서 저장소를 사용한다. 없으면 검증을 끄고 진행한다.

```bash
py -3 -m pip install truststore
```

## 트래픽

10년 × 33개 시군구 × 매매·전월세 = 약 7,200회 요청(API 별로는 각 3,600회).
일일 한도는 활용신청한 API 단위로 계산되므로 개발계정(보통 10,000회)에서 하루에 끝난다.

- 요청 1건은 0.1~0.9초로 빠르다. 다만 **장시간 연속으로 두드리면 429 Too Many Requests**
  가 걸린다. 맞고 나서 길게 쉬면 처리량이 무너지므로, 초당 요청수를 미리 맞춰 보내는
  리미터를 쓴다(`--rate`, 기본 8/초). 429 가 나면 자동으로 감속하고 조금씩 회복한다.
  진행 로그에 현재 속도가 찍힌다.
- 실패한 (구, 월) 은 캐시에 저장하지 않으므로 **다시 실행하면 그 부분만 재시도**한다.
- 캐시는 시군구의 모든 거래를 그대로 담는다. 나중에 단지를 추가해도
  `--aggregate-only` 로 재집계만 하면 되고 다시 받을 필요가 없다.
